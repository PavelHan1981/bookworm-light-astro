## Core Features of AWS Bedrock


**Amazon Bedrock** is a **fully managed Serverless service** provided by AWS. It enables access to high-performance Foundation Models (FMs) from leading AI companies (such as Anthropic, Meta, Mistral, Amazon, etc.) via a unified API, while offering a suite of peripheral features designed for building generative AI applications.


![image.png](/images/blog/AWS-Bedrock服务的调研信息总结-1.png)


Below is a list of the core functional modules provided by Amazon Bedrock:

- Provides a unified Serverless API interface for Foundation Models, enabling access to industry-leading multimodal large language models (including Anthropic, Meta, Mistral, Cohere, AI21 Labs, Amazon's proprietary Titan and Nova models, as well as domestic models such as DeepSeek, GLM, Qwen, and Kimi). It also allows applications to dynamically route model inference requests across multiple AWS regions, thereby improving availability and breaking through throughput limitations of a single region.
- Supports native knowledge base applications and fully managed RAG (Retrieval-Augmented Generation) pipelines. It can automatically connect to backend data sources (such as S3, Confluence, SharePoint, etc.), handle document chunking, convert them into vectors stored in vector databases like OpenSearch, and automatically perform similarity searches and context enhancement when users submit queries.
- Supports model fine-tuning, allowing enterprises to use their own labeled data for supervised fine-tuning of supported models (such as Amazon Titan, Llama, and Cohere) to enhance model accuracy in specific domains.
- Implements an independent, model-agnostic security filtering layer based on Guardrails. It supports custom topic denial policies to filter harmful content generated by models (hate speech, violence, explicit content), intercept prompt injections, and mask PII (Personally Identifiable Information), ensuring that AI outputs comply with enterprise compliance requirements.

## Relationships and Differences Between Amazon Bedrock, SageMaker, and Q


Within the AWS AI ecosystem, the positioning of **Amazon Bedrock**, **Amazon SageMaker**, and **Amazon Q** can superficially appear to overlap in providing AI model access support, making their differences in positioning and usage easily confusing. Below is a detailed explanation of the specific roles of these three services in practice.

1. **Amazon Q: Positioned as an out-of-the-box, enterprise-customized AI assistant**
- Essentially a fully built, enterprise-customized generative AI assistant targeted directly at end-users and developers.
- **Its core feature is the ability to invoke models directly without writing any code, ready to use upon activation.** It is available in several different editions:
    - Amazon Q Developer (formerly CodeWhisperer): Primarily embedded in IDEs (such as VS Code) or the AWS Console to assist with writing code, troubleshooting Lambda errors, or explaining complex IoT Rule SQL snippets.
    - Amazon Q Business: Can be thought of as an enterprise knowledge base for internal employees, allowing companies to connect internal HR documents, IT guidelines, and other resources. Employees can then ask questions directly through the web interface provided by Q Business, complete with strict permission controls (i.e., only answering content the employee is authorized to view).
- Amazon Q is priced per user upon activation; for example, the Amazon Q Business Pro subscription costs approximately $20 per user per month. Consequently, it is positioned as an internal enterprise (To-B/To-E) or developer productivity tool and is not suitable for direct integration into consumer-facing (To-C) applications.
2. **Amazon Bedrock: Positioned as a super gateway for large model APIs (PaaS for GenAI)**
- A fully managed Serverless generative AI service tailored for application developers (Backend/Full-stack Engineers).
- Its core philosophy is that developers do not need to deploy models themselves or manage servers; with just a single line of code (calling an API), they can switch between multiple industry-leading models. Therefore, within the AWS ecosystem, Bedrock serves as the foundation for developers to build their own AI applications, providing model-as-a-service (MaaS) capabilities.
3. **Amazon SageMaker: Positioned as a cloud platform for machine learning model development and training (End-to-End MLOps PaaS)**
- A full-lifecycle machine learning workbench designed for model developers (data scientists and algorithm engineers).
- Using SageMaker for machine learning and AI model development and training requires developers to select specific EC2 instance types (such as `ml.p4d.24xlarge`), configure Jupyter Notebooks, and write model training scripts (PyTorch/TensorFlow).
    - SageMaker can be used not only for developing and training large generative AI models, but also extensively for traditional predictive AI (such as XGBoost, time-series forecasting, etc.).
    - Therefore, if open-source models in the industry fail to meet specific application requirements, developers can design their own model network architectures, collect massive training datasets to train from scratch, or deeply fine-tune existing models. In such scenarios, SageMaker is the appropriate choice.

## Basic Usage Testing of Bedrock Models


Before actually invoking models on Bedrock via code, you need to install the necessary local dependencies and configure the environment properly. Run the following command in your terminal on the current system (Windows) to install AWS CLI v2 (note that you must restart the terminal after the initial installation to use the `aws cli` commands):


```python
msiexec.exe /i https://awscli.amazonaws.com/AWSCLIV2.msi
```


When using the AWS CLI for the first time, you need to create a new access key in the AWS Web Console (IAM - Users / [Username] / Security credentials / Access keys) and configure it in your terminal using the `aws configure` command:


```python
AWS Access Key ID [None]: Your Access Key ID
AWS Secret Access Key [None]: Your Secret Access Key
Default region name [None]: us-east-1 (The region where Bedrock service is hosted)
Default output format [None]: json
```


To query the list of models supported by AWS Bedrock in a specified region along with their corresponding `modelArn`, use the following command:


```python
aws bedrock list-foundation-models --region us-east-1 --query "modelSummaries[*].[modelId, modelArn]" --output table
```


Below is an example of using Python and the AWS `boto3` package to access a specified model on Bedrock:


```python
import boto3
import base64

bedrock_runtime = boto3.client('bedrock-runtime', region_name='us-east-1')

model_id = 'us.amazon.nova-2-lite-v1:0'
image_path = 'bear.png'  # Please replace with your image path

def encode_image(image_path):
    with open(image_path, 'rb') as image_file:
        return base64.b64encode(image_file.read()).decode('utf-8')

try:
    print("Reading image...\n")
    base64_image = encode_image(image_path)
    
    user_prompt = "Please describe the content of this image in detail."
    
    response = bedrock_runtime.converse(
        modelId=model_id,
        messages=[
            {
                "role": "user",
                "content": [
                    {
                        "text": user_prompt
                    },
                    {
                        "image": {
                            "format": "png",  
                            "source": {
                                "bytes": base64.b64decode(base64_image)  # Converse API requires raw bytes
                            }
                        }
                    }
                ]
            }
        ],
        inferenceConfig={
            "maxTokens": 30,
            "temperature": 0.7,
            "topP": 0.9
        }
    )

    response_text = response['output']['message']['content'][0]['text']
    print("🤖 Image Description:\n" + "-"*40)
    print(response_text)
    
    # Check Token consumption
    print("\n" + "="*40)
    print(f"💰 Token Usage Statistics: Input {response['usage']['inputTokens']} | Output {response['usage']['outputTokens']}")

except FileNotFoundError:
    print(f"❌ Error: Image file not found, please check if the path is correct: {image_path}")
except Exception as e:
    print(f"❌ Invocation failed: {e}")
```


As you can see, the process of accessing a Bedrock model is very similar to using HTTP to call API endpoints of various large language models, except that it uses the AWS Boto3 `bedrock_runtime.converse` interface while specifying the `modelId`.
