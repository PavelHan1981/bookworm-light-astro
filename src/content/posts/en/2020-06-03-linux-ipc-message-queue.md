## **Message Queue Fundamentals**

*   The message queue mechanism in Linux systems is one of the three inter-process IPC mechanisms provided by System V IPC: message queues, semaphores, and shared memory.
*   The Linux kernel uses a non-negative integer identifier to refer to each IPC structure (including message queues, semaphores, shared memory, etc.). Whenever an IPC structure is created or an existing one in the kernel is accessed, a key (key_t) must be specified to distinguish between different IPC structures.
*   Each message in a message queue must adhere to system limits: MSGMAX for maximum message length, MSGMNB for the total number of bytes per message queue, and MSGMNI for the total number of message queues on the system.
    *   You can view the specific limit data by checking `/proc/sys/kernel/`.
*   In Linux, the `ipcs` command can be used to view the status and statistical data of message queues present in the system kernel.

## **How Message Queues Work**

Essentially, a message queue is a linked list located in kernel space. A message queue defined and declared in application space actually corresponds to a set (multiple) of linked lists in kernel space. Each message sent and received at the user layer corresponds to a node in a linked list. Message nodes of the same message type are linked together by pointers in the order they were written, so each message type has its own linked list.

At its core, application-layer sending and receiving operations on a message queue are based on a specific linked list within it, rather than the entire message queue.

The principle of the message queue data structure in the kernel is shown in the figure below:

![Untitled.png](/images/blog/Linux-IPC机制之消息队列-1.png)

*   The message type ID is represented by an integer, and this ID must be greater than 0. Each message type has its own linked list.
*   The application layer must specify a message type ID when sending and receiving messages, so that the kernel knows which linked list to put the message into or retrieve data from.
*   A node with message type ID 0 is used to record the order in which all messages join the entire message queue, i.e., the chain marked with a red line in the diagram above.
    *   In an application, if we need to read all messages in the entire message queue in order, meaning we want all messages returned regardless of their message type ID, we can specify message type ID 0 when reading. This will return all messages in the entire message queue in sequential order.

## **Key Message Queue APIs**

**`ftok` function**

*   Used to generate a message queue key based on parameters. Its prototype is:
    ```c
    key_t ftok(const char *pathname, int proj_id);
    ```
*   Parameters:
    *   `pathname`: The path name of an existing file or directory in the file system. It can be set arbitrarily, but the file/directory corresponding to this path name must exist.
    *   `proj_id`: Can be set arbitrarily according to your own convention; in Unix systems, the value range is 0-255.
*   Function: The `ftok` function extracts the inode information of the file at the given `pathname` from the system. It then combines this file information with the passed `proj_id` to generate a unique message queue key.

**`msgget` function**

*   Used to create/access a message queue. Its prototype is:
    ```c
    int msgget(key_t key, int msgflag);
    ```
*   Parameters:
    *   `key`: The message queue key, usually generated by `ftok()`.
    *   `msgflag`: Has two options, `IPC_CREAT` and `IPC_EXCL`.
    *   Using `IPC_CREAT` alone: If the message queue does not exist, create it; if it exists, open and return its ID.
    *   Using `IPC_CREAT | IPC_EXCL`: If the message queue does not exist, create it; if it exists, return an error.
*   Return Value:
    *   On success, returns a non-negative integer representing the message queue ID, which is needed for subsequent sending and receiving operations. On failure, returns -1.

**`msgctl` function**

*   Used to control and set message queue properties. Its prototype is:
    ```c
    int msgctl(int msqid, int cmd, struct msqid_ds *buf);
    ```
*   Parameters:
    *   `msqid`: The message queue ID returned by the `msgget` function.
    *   `cmd`: Has three options: `IPC_STAT`, `IPC_SET`, `IPC_RMID`.
    *   `IPC_STAT`: Retrieves internal attribute information (uid, gid, byte count, message count, etc.) of the message queue and assigns it to the `msqid_ds` structure passed as a parameter.
    *   `IPC_SET`: Uses the `msqid_ds` structure data passed as a parameter to set modifiable attributes of the message queue (requires sufficient permissions, and only modifiable parts can be set).
    *   `IPC_RMID`: Deletes the message queue.
*   Return Value:
    *   Returns 0 on success, -1 on failure.

**`msgsnd` function:**

*   Sends a message to the message queue. Its prototype is:
    ```c
    int msgsnd(int msqid, const void *msgp, size_t msgsz, int msgflg);
    ```
*   Parameters:
    *   `msqid`: The message queue ID returned by the `msgget` function.
    *   `msgp`: The message content to be sent.
    *   The first `sizeof(long int)` bytes of the message content *must* be the message type ID. Otherwise, the kernel will not know which linked list to process this message on after receiving it.
    *   `msgsz`: The length of the message to be sent.
        *   This message length should exclude the length of the message type ID, i.e., `sizeof(long int)`.
    *   `msgflg`:
        *   Defaults to 0, meaning block and wait if the message queue is full.
        *   Set to `IPC_NOWAIT` to return an error immediately if the message queue is full.
*   Return Value:
    *   Returns 0 on success, -1 on failure.
*   Notes:
    *   The size of the sent message must be less than the system-defined upper limit, i.e., the `MSGMAX` parameter.
    *   The message structure *must* begin with a `long int` type. The kernel uses this value in the message to determine which linked list it should be placed into, and the message receiver also uses this value to determine the type of message to be received.

**`msgrcv` function**

*   Used to receive messages from a message queue. Its prototype is:
    ```c
    ssize_t msgrcv(int msqid, void *msgp, size_t msgsz, long msgtyp, int msgflg);
    ```
*   Parameters:
    *   `msqid`: The message queue ID returned by the `msgget` function.
    *   `msgp`: Pointer to the received message buffer.
    *   `msgsz`: The length of the received message.
    *   `msgtyp`: Specifies the message type to be received.
        *   `msgtyp = 0`: Retrieves the first message from the entire message queue. Repeatedly reading with `msgtyp = 0` will read all messages from the entire message queue in order, regardless of their specific type.
        *   `msgtyp > 0`: Retrieves the first message of type `msgtyp`, unless `msgflg` is set to `MSG_EXCEPT`, which means retrieving the first message *other than* type `msgtyp`.
        *   The above can be understood in conjunction with the message queue linked list structure described earlier.
    *   `msgflg`:
        *   Defaults to 0, meaning block and wait if there are no messages of the specified type in the message queue.
        *   Set to `IPC_NOWAIT` to return an error immediately if there are no messages of the specified type in the message queue.
*   Return Value:
    *   On success, returns the number of characters actually received into the receive buffer. On failure, returns -1.

## **Example Code**

Here, a typical message queue communication scenario is designed: it supports sending messages with different content to different message type linked lists within the same message queue, and correctly receiving and parsing them.

*   Create a message queue. The `send` process writes messages to this queue, and the `recv` process reads messages from the message queue.
*   The `send` process sends messages to different message types within the message queue in a single execution.
*   This is equivalent to sending messages to multiple linked lists of a single message queue.
*   The `send` process sends messages with different content to the same message type within the message queue in a single execution.
*   This is equivalent to writing different types of message data to the same message linked list of a single message queue.

`msg.h`:

```c
#ifndef _MSG_H_
#define _MSG_H_

#define msg_file_path "/home/embedded/pavelhan"
#define msg_project_id 'H'

typedef struct {
    unsigned int cmd;
    char name[20];
    int age;
}Person;

typedef struct {
    unsigned int cmd;
    int age;
    char name[20];
}Dog;

typedef struct {
    long type;
    Person person;
}Person_Msg;

typedef struct {
    long type;
    Dog dog;
}Dog_Msg;

#endif
```

`send.c`:

```c
#include <unistd.h>
#include <sys/ipc.h>
#include <sys/msg.h>
#include <stdio.h>
#include <stdlib.h>

#include "msg.h"

void printPersonMsg(Person_Msg *msg) {
    printf("{ cmd = %ld, name = %s, age = %d }\n",
           msg->person.cmd, msg->person.name, msg->person.age);
}

void printDogMsg(Dog_Msg *msg) {
    printf("{ cmd = %ld, name = %s, age = %d }\n",
           msg->dog.cmd, msg->dog.name, msg->dog.age);
}

int main(int argc, char *argv) {
    key_t msq_key = ftok(msg_file_path,msg_project_id);
    printf("msg queue key:%x\n", msq_key);

    int msq_id = msgget(msq_key, IPC_CREAT | 0664);
    if(msq_id<0){
        perror("Create msg queue failed\n");
        exit(-1);
    }

    Person_Msg person_msg[10] = {
        {1, {1, "Luffy", 17}},
        {1, {1, "Zoro", 19}},
        {2, {1, "ami", 18}},
        {2, {1, "Usopo", 17}},
        {1, {1, "Sanji", 19}},
        {3, {1, "Chopper", 15}},
        {4, {1, "Robin", 28}},
        {4, {1, "Franky", 34}},
        {5, {1, "Brook", 88}},
        {6, {1, "Sunny", 2}}
    };
    
    Dog_Msg dog_msg[10] = {
        {1, {2, 2, "hhh"}},
        {1, {2, 3, "zzz"}},
        {2, {2, 0, "aaa"}},
        {2, {2, 1, "Uuuu"}},
        {1, {2, 2, "Sss"}},
        {3, {2, 5, "Cccc"}},
        {4, {2, 6, "Rrrr"}},
        {4, {2, 3, "Ffff"}},
        {5, {2, 2, "Bbb"}},
        {6, {2, 3, "Ssss"}}
    };

    int i;
    for (i = 0; i < 10; ++i) {
        int res = msgsnd(msq_id, &person_msg[i], sizeof(unsigned int)+sizeof(Person), 0);
        if(res>=0){
            printPersonMsg(&person_msg[i]);
        }
    }

    for (i = 0; i < 10; ++i) {
        int res = msgsnd(msq_id, &dog_msg[i], sizeof(unsigned int)+sizeof(Dog), 0);
        if(res>=0){
            printDogMsg(&dog_msg[i]);
        }
    }
    
    return 0;
}
```

`recv.c`:

```c
#include <unistd.h>
#include <sys/types.h>
#include <sys/ipc.h>
#include <sys/msg.h>
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>

#include "msg.h"

void printPersonMsg(Person_Msg *msg) {
    printf("{ cmd = %ld, name = %s, age = %d }\n",
           msg->person.cmd, msg->person.name, msg->person.age);
}

void printDogMsg(Dog_Msg *msg) {
    printf("{ cmd = %ld, name = %s, age = %d }\n",
           msg->dog.cmd, msg->dog.name, msg->dog.age);
}

unsigned char msg_buf[4096];

int main(int argc, char *argv[]) {
    int flag;

    if (argc < 2) {
        printf("usage: %s <type>\n", argv[0]);
        return -1;
    }
    
    // 要获取的消息类型
    long type = atol(argv[1]);
    
    key_t msq_key = ftok(msg_file_path,msg_project_id);
    printf("msg queue key:%x\n", msq_key);

    int id = msgget(msq_key, IPC_CREAT | 0664);
    if(id<0){
        perror("Create msg queue failed\n");
        exit(-1);
    }
    
    system("ipcs -q") ;
    
    int res;    
    while(1) {
        // 以非阻塞的方式接收类型为 type 的消息
        res = msgrcv(id, msg_buf, sizeof(msg_buf), type, IPC_NOWAIT);
        if (res < 0) {
            // 如果消息接收完毕就退出，否则报错并退出
            if (errno == ENOMSG) {
                printf("No message!\n");
                break;
            }
        }
        // 打印消息内容
        unsigned int cmd;
        cmd=*(unsigned int *)(msg_buf+sizeof(long));
        if(cmd==1){
            Person_Msg * person_msg;
            person_msg=(Person_Msg *)msg_buf;
            printPersonMsg(person_msg);
        }
        else if(cmd==2){
            Dog_Msg * dog_msg;
            dog_msg=(Dog_Msg *)msg_buf;
            printDogMsg(dog_msg);
        }
    }

    flag = msgctl(id, IPC_RMID,NULL) ;
    if ( flag < 0 ){
        perror("rm message queue error") ;
        return -1 ;
    }
    system("ipcs -q") ;
    return 0;
}
```

## **Considerations for Using Message Queues in Linux Application-Layer Multi-Module Applications**

*   Multi-module applications are generally architecturally divided into a main module and multiple sub-modules. During application startup, the main module is launched first, and it then decides to launch the various sub-modules based on configuration or startup parameters.
    *   The main module is also responsible for deleting all message queues upon exit to prevent state confusion during subsequent startups.
*   Each module has its own independent message queue. All message queues are created when the main module starts. After each sub-module starts, it attaches to the main module's message queue and its own message queue using `msgget`.
    *   All sub-modules will only communicate directly with the main module via message queues; they will not send messages directly to other modules. Messages are managed and relayed by the main module to reduce coupling between sub-modules.
    *   Therefore, each sub-module only needs to attach its own message queue and the main module's message queue. For the main module, since it may communicate with all sub-modules, it needs to create/attach its own message queue and those of all sub-modules.
*   All modules (including the main module) have a dedicated message handling thread for receiving and processing information in their own message queues. Within this thread, a `while` loop with blocking `msgrcv` waits to receive and process messages sent to itself. Here, the `msgrcv` function should use `msgtyp=0` as the reception parameter, allowing it to receive and process all messages from all linked lists within the entire message queue indiscriminately. After receiving a message, different processing logic can then be applied based on different message types.
*   All modules (including the main module) only need to call `msgsnd` to send messages when they need to send messages to other modules. Different message type IDs can be specified in the `msgtyp` parameter to distinguish between different message contents.
    *   As shown in the example code above, different message types can contain different message data structures. However, generally, since message queues themselves have a limit on the total number of bytes, it is not recommended to use message queues for direct transfer of large data. Processes can cooperate with shared memory for large data structure transfers, while threads can pass message data through global data structures.
